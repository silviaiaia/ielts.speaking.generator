A web app that generates IELTS Speaking practice questions on demand for
Parts 1, 2 and 3. Nothing to install — pick a part and a topic, and a fresh
question set is generated by Gemini.

**[→ Try it](https://ielts-speaking-generator.vercel.app/)**

## Features

- **Part 1** — four warm-up questions on one topic, ordered the way an
  examiner asks them: concrete first, most open-ended last.
- **Part 2** — a full cue card with the `Describe...` task, three bullet
  prompts and the closing `and explain...` line, plus the two follow-ups
  an examiner asks after the two-minute turn.
- **Part 3** — four discussion questions that climb from everyday
  observation to speculation and evaluation.
- **28 topics**, or let the app pick one for you.

## How it works

```
Browser ──POST /api/generate_question──▶ Vercel serverless function
                                                    │
                                          Gemini API (key server-side)
                                                    │
Browser ◀───────── structured JSON ─────────────────┘
```

The browser never sees the Gemini API key. Calling the model directly
from client-side JavaScript would expose it to anyone opening DevTools,
so all requests are proxied through a serverless function that reads the
key from an environment variable. The model name is an environment
variable too (`GEMINI_MODEL`) — when `gemini-2.0-flash` was retired,
swapping it was a config change rather than a code change.

## Prompt design

The interesting part of this project is not the API call, it is getting
a language model to behave like a consistent exam item writer. Three
things do most of the work, all in [`api/prompts.js`](api/prompts.js).

**A schema instead of a format request.** Each part declares a
`responseSchema`, and Gemini is called with
`responseMimeType: "application/json"`. The model cannot return prose,
a preamble, or markdown the front end has to guess at — a Part 2
response is always `{ task, bullets[3], explainPrompt, followUps[2] }`.
The front end renders fields, so it never parses text.

**Two axes of variety, to stop the model repeating itself.** Asked for
"an IELTS question" with nothing else to go on, a model collapses onto
the same handful of textbook topics — hometown, favourite food,
hobbies — however high you set the temperature. So every request is
seeded with both a topic (28 of them) and a randomly drawn *angle* to
come at it from: for Part 1, one of "how often they do it", "how it has
changed for them over the last few years", "a comparison between two
options", and so on. That is roughly 170 distinct starting points per
part, and because the angle is always random, picking the same topic
twice still gives different questions.

**Constraints that encode the actual exam.** The system instruction
fixes the examiner persona and the accessibility bar — understandable
to a Band 5 candidate, open enough for a Band 8, answerable by an adult
anywhere regardless of country, income or family situation. The
per-part prompts then pin the format down: Part 1 questions must be
answerable in 20–40 seconds and stay under 20 words; a Part 2 card's
closing line must ask for a reason or a feeling rather than one more
fact; Part 3 questions must be about society rather than the
candidate's own life. Common textbook items are named and banned
outright.

### Two things the model does that the docs do not warn you about

`gemini-3.6-flash` is a thinking model, and thought tokens are billed
against `maxOutputTokens`. At 1024 the JSON came back truncated
mid-string. Writing four exam questions to a fixed schema is not a
reasoning task, so the fix was `thinkingLevel: LOW` plus headroom —
which also cut latency.

The API returns `503 UNAVAILABLE` under load often enough to matter, so
transient statuses are retried with exponential backoff. `429` is
deliberately *not* retried: the free tier allows five requests a minute
and the quota error asks for a ~20s wait, which outlasts the serverless
function's own timeout, so retrying would time out *and* spend another
unit of quota on the way. Retries are capped at three for the same
reason — every retry is itself a metered request, and a run of 503s
would otherwise turn a recoverable outage into a 429 for the next user.
The free tier meters per minute *and* per day (20 requests), and the two
need different advice, so the 429 handler tells them apart rather than
telling someone to wait thirty seconds for an allowance that resets
tomorrow.

## API

| Endpoint | Method | Body | Returns |
| --- | --- | --- | --- |
| `/api/health` | GET | — | `{ status, model }` |
| `/api/topics` | GET | — | `{ topics: [{ id, label }] }` |
| `/api/generate_question` | POST | `{ part, topic? }` | the question set |

`part` is `part1`, `part2` or `part3`. `topic` is optional — omit it and
the server draws one at random. The topic catalogue is served from
`/api/topics` so the front-end picker is built from it rather than
duplicating the list.

## Running locally

```bash
git clone https://github.com/silviaiaia/ielts.speaking.generator.git
cd ielts.speaking.generator
npm install

echo "GEMINI_API_KEY=your_key_here" > .env
npm run dev
```

Get a key from [Google AI Studio](https://aistudio.google.com/apikey),
then open `http://localhost:3000`. Note that the free tier allows only
20 requests per day, which a testing session goes through quickly. To
hit the API directly:

```bash
curl -X POST http://localhost:3000/api/generate_question \
  -H "Content-Type: application/json" -d '{"part":"part2","topic":"travel"}'
```
